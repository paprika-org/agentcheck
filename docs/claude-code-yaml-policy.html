Claude Code YAML Policy: Practical Guardrails for Tool Use and Agent Behavior

A claude code yaml policy is useful when you want reproducible restrictions on what an agent can do, not just a prompt asking it to behave. If your workflow includes shell access, file writes, or network-capable tools, policy needs to live outside the model. That is the gap AgentCheck targets: it wraps each Claude process with hook-based guardrails, logs tool calls to JSONL, and enforces YAML rule packs that constrain behavior.

Why a Claude Code YAML Policy Matters

Prompt instructions are soft control. They are easy to bypass accidentally, hard to audit, and difficult to review in code. A policy file is different: it can be versioned, diffed, code-reviewed, and pinned to a repository. For teams running agents in CI, release automation, or internal developer tooling, that difference matters.

The practical value of a claude code yaml policy is that it moves governance into configuration. Instead of hoping the model avoids dangerous commands, you define what is denied, what is allowed, and what gets logged. That gives you deterministic constraints around behaviors like writing outside the repo, running destructive shell commands, or invoking tools you do not want in a given environment.

This is not a magic security boundary. Policy wrappers are strongest when paired with ordinary hardening: least-privilege credentials, container isolation, read-only mounts where possible, and narrow CI tokens. Still, YAML policy is the missing middle layer between “trust the prompt” and “lock down the entire machine.”

Installing AgentCheck and Defining a Policy

AgentCheck is distributed as a global npm install from GitHub. The main idea is simple: install the wrapper, define a rule pack in YAML, and run Claude Code through that wrapper so every tool call is checked and logged.

npm install -g github:paprika-org/agentcheck

# example rule pack
cat > policy.yaml <<'YAML'
name: repo-safe
rules:
  - id: deny-destructive-shell
    match:
      tool: shell
      command_regex: '(rm -rf|sudo|chmod 777)'
    action: deny

  - id: allow-readme-edit
    match:
      tool: write_file
      path_regex: '^docs/|^README\.md$'
    action: allow

  - id: deny-outside-workspace
    match:
      tool: write_file
      path_regex: '^/|^\.\./'
    action: deny
YAML

# illustrative invocation; adjust to your local workflow
agentcheck --policy ./policy.yaml -- claude

The exact schema and invocation details should come from the project docs, but the pattern is clear. A rule pack matches on tool metadata such as tool name, command text, or path, then applies an action. The useful part is not just blocking. Logging every checked call into JSONL means you can inspect what the agent attempted, what matched, and what was denied.

How to Structure a Useful Claude Code YAML Policy

Start with behavior categories instead of individual commands. Most teams care about four things: shell execution, filesystem writes, network access, and secret exposure. Model your rules around those categories. That keeps the policy readable and reduces the chance of accidental gaps.

A good first version usually denies obviously destructive shell patterns, restricts writes to the repository or a specific subdirectory, and logs everything. After that, tighten based on real audit data. If agents only need to modify src/ and tests/, do not allow broad writes elsewhere. If package installation is only acceptable in ephemeral CI, keep it disabled locally.

Prefer narrow allow rules over giant deny lists. Deny lists are brittle because they try to enumerate bad behavior. Allow rules are easier to reason about: “the agent may edit files under these paths and run these commands.” The more privileged the environment, the more this matters.

Policy should fail closed where practical. If your wrapper supports it, unmatched tool calls should be denied or at least surfaced loudly in logs.

Honest Limitations and Operational Tradeoffs

A claude code yaml policy is enforcement around visible tool calls, not a formal proof of safety. If the host process already has broad credentials or the wrapper sees only part of the execution graph, policy cannot compensate for that. Likewise, regex-heavy rule packs can become fragile if you overfit them to command strings instead of modeling intent.

There is also a developer-experience tradeoff. Tight policies reduce risk, but they also create friction when legitimate work expands. Expect a tuning period. In practice, teams should treat policy changes the same way they treat CI or deployment rule changes: review them, test them, and keep them small.

Another limitation is semantic ambiguity. A rule can block rm -rf, but it may not understand whether a harmless-looking script indirectly performs the same action. That is why policy should be layered with operating-system controls and careful tool design. AgentCheck gives you a behavioral governance layer, not a replacement for system security.

Common Mistakes

The first common mistake is writing a policy that only denies a few scary commands and assumes the rest is safe. That leaves a large implicit allow surface. If you care about control, start from what the agent actually needs and permit only that.

The second mistake is ignoring logs after adding enforcement. JSONL logging is not just an audit artifact for incidents; it is how you discover noisy rules, accidental denies, and privilege you forgot to remove. Without reviewing real tool-call data, policy quality stagnates.

A third pitfall is treating path regexes casually. Overbroad expressions can allow writes outside intended directories or fail on relative-path edge cases. Test policies against representative commands before you rely on them.

Frequently Asked Questions

What is a Claude Code YAML policy?

It is a YAML rule pack that defines what a Claude Code session may do, such as allowing or denying tools, constraining paths, and enforcing behavioral checks through a wrapper like AgentCheck.

Does a YAML policy replace sandboxing?

No. A YAML policy is an application-layer control. It complements OS sandboxing, container restrictions, and repository permissions, but it should not be treated as a kernel-level security boundary.

Can I audit what the agent actually did?

Yes. AgentCheck logs tool calls to JSONL, which makes it easier to review command history, file access, and enforcement outcomes after a run.

What are the limits of policy-based control?

Policies can constrain the wrapper-visible actions, but they cannot fix unsafe host configuration, overbroad credentials, or tools that themselves have too much authority.
